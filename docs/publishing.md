# PyPI release preparation

These are **candidate** workflows, not evidence that either project exists on PyPI. Keep using the source-checkout installation instructions until publication is independently verified. The distributions are independently versioned:

| Distribution | Project directory | First release tag | PyPI trusted publisher workflow filename | PyPI environment field |
| --- | --- | --- | --- | --- |
| `safurrier-context-engineering` | `packages/context-engineering` | context-engineering-v2.6.0 | publish-context-engineering.yml | Leave blank |
| `safurrier-writing-check` | `packages/writing-check` | writing-check-v1.0.0 | publish-writing-check.yml | Leave blank |

Only publishing a GitHub Release on an exact matching tag routes to the corresponding job; push, PR, and draft releases do not deploy. The tag must identify the same version as that package's `pyproject.toml`. The workflow checks the release identity, tag target, full repository fast check, and built wheel/sdist at the release event commit in a job without OIDC. A separate minimal-permission OIDC upload job receives only the validated artifacts and checks their digest before the trusted-publisher upload. Each release uploads exactly one distribution. Do not use an unreviewed tag, release, or artifact.

Before enabling a first release, repository and PyPI owners must:

1. Confirm ownership/availability and existing versions of **each** exact PyPI project name, release authority, and permitted first version; never overwrite an existing version. Confirm the packaged portable source and the vendored Google Vale policy/license/provenance are cleared for public redistribution, including no private corpus, credentials, or machine-specific material.
2. The repository stays private on the current GitHub Free plan. This first-release path has **no enforced environment reviewer gate or release-tag protection rules**: anyone with sufficient repository release/tag or workflow authority could trigger publication. Before any tag or GitHub Release, the account owner must manually approve the proposed source commit and tag target, prior CI results, locally built artifacts, and public redistribution. Review release CI and its artifacts after the workflow runs; there is no pause for approval before its upload. Manual review is a procedure, not a GitHub-enforced safeguard. In the PyPI account's pending-publisher form, enter each exact distribution name above, GitHub owner `safurrier`, repository `skills`, its exact workflow filename from the table (filename only, not a path), and **leave the environment field blank**. If a project already exists, configure the same tuple as a trusted publisher in that project's settings instead. PyPI's [pending-publisher guidance](https://docs.pypi.org/trusted-publishers/creating-a-project-through-oidc/) confirms that the GitHub Actions environment is optional; a pending publisher does not reserve the project name before first use. Do not add a PyPI API token or repository secret.
3. Review the source at the release tag, its changelog and metadata, run `python scripts/fast_check.py`, and build each intended package in an empty output directory. Run `python scripts/check_publish.py <package-key> refs/tags/<tag> <tag> --dist <dist-directory>`; inspect the wheel/sdist, notices and provenance. For Writing Check, verify the pinned `vale` dependency's first-use executable download behavior and network/prerequisite expectations in a clean environment. CI cannot establish private-source rights or PyPI namespace ownership.
4. Only after review and approval, create the corresponding tag and publish its GitHub Release. The release workflow must be present on the default branch. Observe the workflow, verify the uploaded project/version and clean installation before changing installation guidance. No publication is part of this preparation branch.
